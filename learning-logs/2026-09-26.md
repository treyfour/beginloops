Today's focus: **Webhooks — idempotency and duplicate delivery**

Webhook providers (GitHub, Stripe, Vercel) guarantee *at-least-once* delivery — not exactly-once. If your endpoint is slow or returns a 5xx, they'll retry. Without protection, you'll process the same event twice: charge a card twice, send two emails, run a migration twice.

Add this pattern to `app/api/webhooks/route.ts`:

```ts
// In-memory store — replace with Redis/DB in production
const processedEventIds = new Set<string>();

export async function POST(request: Request) {
  const body = await request.json();

  // Most providers include a unique event ID in the payload or headers
  const eventId =
    request.headers.get("x-github-delivery") || // GitHub
    request.headers.get("stripe-signature")?.split(",")[0] || // Stripe (use full sig as key)
    body?.id;

  if (eventId && processedEventIds.has(eventId)) {
    console.log(`[webhook] duplicate event ignored: ${eventId}`);
    return Response.json({ status: "already_processed" }, { status: 200 });
  }

  if (eventId) {
    processedEventIds.add(eventId);
    // Prune to avoid unbounded memory growth in long-running deploys
    if (processedEventIds.size > 10_000) {
      const [first] = processedEventIds;
      processedEventIds.delete(first);
    }
  }

  console.log("[webhook] received:", JSON.stringify(body, null, 2));
  return Response.json({ status: "ok" });
}
```

**Why this matters:** Every real webhook receiver needs this. The `Set` approach works fine in development and single-instance deploys. In production across multiple Vercel instances, swap the `Set` for a Redis `SETNX` call with a TTL — same concept, distributed. Understanding this distinction (in-process vs. distributed state) is the key insight that separates toy implementations from production ones.

> **Real-world use:** Stripe's official docs explicitly warn about duplicate events and recommend idempotency keys. GitHub's webhook docs note that delivery is at-least-once. This pattern handles both.
