Today's focus: **Crons — securing your cron endpoints**

Your heartbeat cron is already running on a schedule, but right now anyone who knows the URL can hit it directly. Vercel has a built-in fix: it sends an `Authorization: Bearer <CRON_SECRET>` header with every scheduled invocation. You just need to check for it:

```ts
// app/api/cron/heartbeat/route.ts
import { NextResponse } from "next/server";

export async function GET(req: Request) {
  // Guard: only Vercel's scheduler can trigger this
  const auth = req.headers.get("authorization");
  if (auth !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response("Unauthorized", { status: 401 });
  }

  const base = process.env.VERCEL_URL
    ? `https://${process.env.VERCEL_URL}`
    : "http://localhost:3000";

  // ... rest of your existing handler unchanged
}
```

Then add the secret to your environment:

```bash
# .env.local (for local testing)
CRON_SECRET=some-long-random-string

# Also add it in your Vercel dashboard → Settings → Environment Variables
# Vercel reads this and automatically injects it into cron request headers
```

Test locally that the guard works:

```bash
# Should get 401 — no secret
curl http://localhost:3000/api/cron/heartbeat

# Should get 200 — correct secret
curl http://localhost:3000/api/cron/heartbeat \
  -H "Authorization: Bearer some-long-random-string"
```

**Why this matters:** This is the same "shared secret" pattern used everywhere in webhooks and crons. Vercel crons → `CRON_SECRET`. GitHub webhooks → `x-hub-signature` HMAC. Stripe webhooks → `stripe-signature` HMAC. The concept is identical: the caller proves identity with a secret, and the handler rejects anything that can't prove it. Once you add this, your cron endpoint is hardened for production.
