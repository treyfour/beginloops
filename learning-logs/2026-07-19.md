## Suggested next step
**Create `app/api/status/route.ts` — a tiny module-level cache so the heartbeat cron has somewhere to write its result.**

This is the *smallest* change that unlocks all the UI work: without it, the heartbeat result disappears after every serverless invocation and there is nothing for the page to display.

```ts
// app/api/status/route.ts
import { NextRequest, NextResponse } from "next/server";

interface Status {
  status: "ok" | "degraded" | "unknown";
  timestamp: string | null;
  checks: { webhookEndpoint: "ok" | "unreachable" } | null;
}

let cache: Status = { status: "unknown", timestamp: null, checks: null };

export function GET() {
  return NextResponse.json(cache);
}

export async function POST(req: NextRequest) {
  cache = await req.json();
  return NextResponse.json({ ok: true });
}
```

Then add one fetch call at the bottom of `app/api/cron/heartbeat/route.ts`, before the final `return`, to write the result into the new cache:

```ts
await fetch(`${base}/api/status`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(payload),
});
```

(`base` is already defined earlier in that file.)

**Why this matters:** Module-level variables in Next.js serverless functions survive across requests *within a warm instance* — this is the simplest possible persistence layer. Understanding its limits (resets on cold start, not shared across multiple instances) is exactly the lesson that motivates reaching for Vercel KV, Redis, or a database next. Once the status route exists, you can fetch it from `app/page.tsx` and finally see something useful on screen.
