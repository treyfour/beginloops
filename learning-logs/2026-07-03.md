## Suggested next step
Add a `/api/status` route that makes your heartbeat results queryable instead of just logging them to Vercel's console output.

```ts
// app/api/status/route.ts
import { NextResponse } from "next/server";

// Module-level store — survives warm serverless invocations, resets on cold start.
// For real persistence across cold starts, swap this for Vercel KV or a database.
const heartbeatLog: Array<{ status: string; timestamp: string; checks: Record<string, string> }> = [];

export function recordHeartbeat(entry: typeof heartbeatLog[number]) {
  heartbeatLog.unshift(entry);  // newest first
  heartbeatLog.splice(10);      // keep last 10 entries only
}

export async function GET() {
  const latest = heartbeatLog[0] ?? null;
  return NextResponse.json({
    healthy: latest?.status === "ok",
    lastHeartbeat: latest?.timestamp ?? null,
    recentBeats: heartbeatLog,
  });
}
```

Then update `app/api/cron/heartbeat/route.ts` to call `recordHeartbeat(payload)` before returning:

```ts
// add to app/api/cron/heartbeat/route.ts
import { recordHeartbeat } from "../../../status/route";

// inside GET(), after building `payload`:
recordHeartbeat(payload);
return NextResponse.json(payload);
```

**Why this matters:** A heartbeat that nobody reads is just noise in a log. The value comes from making that signal *queryable* — this is exactly how uptime monitors work. They poll a `/health` or `/status` endpoint and alert when it stops responding or returns a bad status. Wiring your cron to *write* state and your status route to *read* it completes the full heartbeat loop: cron fires → probe runs → result is stored → `/api/status` reports it to anyone who asks. From here, adding Vercel KV would give you real persistence across cold starts, and adding a `fetch` to an external monitor (Uptime Robot, Better Uptime) would make it production-grade.
