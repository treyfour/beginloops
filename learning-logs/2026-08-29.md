Today's focus: **Crons**

Vercel automatically injects a `CRON_SECRET` environment variable into every cron invocation via an `Authorization: Bearer <secret>` header. Your heartbeat route ignores this header today, which means anyone who discovers the URL can trigger it on demand — polluting your logs and burning compute. The fix is one small guard at the top of the route handler.

**Step 1 — add the authorization check to `app/api/cron/heartbeat/route.ts`:**

```ts
import { NextResponse } from "next/server";

export async function GET(req: Request) {
  // Vercel automatically sets CRON_SECRET and sends it as a Bearer token
  // on every scheduled invocation. Reject anything that doesn't match.
  const authHeader = req.headers.get("authorization");
  const cronSecret = process.env.CRON_SECRET;

  if (cronSecret) {
    if (authHeader !== `Bearer ${cronSecret}`) {
      console.warn("[heartbeat] rejected: missing or invalid CRON_SECRET");
      return NextResponse.json({ error: "unauthorized" }, { status: 401 });
    }
  }

  // …rest of existing heartbeat logic unchanged…
  return NextResponse.json({
    status: "ok",
    timestamp: new Date().toISOString(),
  });
}
```

**Step 2 — confirm the secret is in your Vercel project:**

Vercel injects `CRON_SECRET` automatically for Pro/Enterprise accounts — you do **not** set it yourself. To verify it's present:

1. Open Vercel Dashboard → your project → **Settings → Environment Variables**
2. Look for `CRON_SECRET` — if it exists, Vercel manages it; if not, you're on a plan where cron auth is not automatic and you should generate and set one yourself:
   ```bash
   openssl rand -hex 32
   # paste the output as CRON_SECRET in Vercel's environment variables
   ```

**Step 3 — test locally without a secret (safe dev mode):**

The `if (cronSecret)` guard means the check is skipped when the variable is absent — so your local `npm run dev` still responds normally to a plain `curl http://localhost:3000/api/cron/heartbeat`. In production, Vercel always has the secret set, so the guard is always enforced there.

```bash
# Local dev — no secret needed → 200
curl http://localhost:3000/api/cron/heartbeat

# Simulate Vercel's call (replace xxx with your actual secret)
curl -H "Authorization: Bearer xxx" http://localhost:3000/api/cron/heartbeat

# Simulate a bad actor → 401
curl -H "Authorization: Bearer wrongsecret" http://localhost:3000/api/cron/heartbeat
```

**Three concepts to lock in:**

1. **Why does Vercel inject `CRON_SECRET` automatically?** Scheduled functions run server-side with no user to authenticate them — the secret is Vercel's way of proving to *your code* that the caller is the scheduler, not a random HTTP client. It's the same pattern as `GITHUB_WEBHOOK_SECRET`, just for internal infra instead of an external service.

2. **Why `if (cronSecret)` instead of always enforcing?** Guards that crash in local dev slow you down. When the variable is absent, skip the check — your laptop isn't Vercel, so there's nothing to verify. When it's present (production), enforce strictly. This pattern — "only validate what's configured" — shows up in every secure webhook and cron handler.

3. **What's the broader principle?** Every inbound entry point in your app should require proof of identity: `CRON_SECRET` for scheduled jobs, `HMAC-SHA256` for webhooks, a session token for user-facing API routes. You now have two of the three — get this guard in place and the cron side of your app is locked down.
