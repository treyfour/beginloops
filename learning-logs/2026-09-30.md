Today's focus: **Webhooks — persisting events so your UI can actually show them**

Your webhook handler receives events and immediately discards them (only `console.log`). In production you'd use a database or queue, but in development the fastest way to see the pattern is a `global` store — Next.js keeps the same module instance alive across hot-reloads when you use `global`.

Add this to the **top** of `app/api/webhooks/route.ts`:

```ts
// A module-level store that survives hot reloads in dev
const g = globalThis as typeof globalThis & {
  _webhookEvents?: Array<{ at: string; event: string; summary: unknown }>;
};
if (!g._webhookEvents) g._webhookEvents = [];
const eventLog = g._webhookEvents;
const MAX_EVENTS = 20;
```

Then inside your `POST` handler, after the switch on `event`, push to the log before returning:

```ts
eventLog.unshift({ at: new Date().toISOString(), event, summary });
if (eventLog.length > MAX_EVENTS) eventLog.pop(); // keep only the last 20
```

Then add a `GET` handler at the bottom of the same file:

```ts
export async function GET() {
  return NextResponse.json(eventLog);
}
```

Now `curl http://localhost:3000/api/webhooks` returns the last 20 events your cron probe has fired — immediately useful for the `useHeartbeat` UI hook that's been waiting to be built.

**Why `global` and not a module-level `const`?** Next.js App Router re-instantiates route module files on each hot reload in dev, resetting any `const` array to `[]`. Writing to `globalThis` survives that reset. In production this doesn't matter because you'd replace it with Redis or a DB — but the pattern of "use `global` in dev, real storage in prod" is a standard Next.js idiom worth knowing.
