Today's focus: **Crons — authenticating who is allowed to trigger a scheduled route**

Right now `/api/cron/heartbeat` is a public GET endpoint — any browser, script, or bot can call it. Vercel sends an `Authorization: Bearer <secret>` header on every cron invocation; checking that header is the standard way to lock the route down.

**Step 1 — Add the secret to your environment.** In Vercel project settings, add `CRON_SECRET=<some-long-random-string>`. Also add it to `.env.local` for local testing.

**Step 2 — Add an auth check at the top of the handler in `app/api/cron/heartbeat/route.ts`:**

```ts
import { NextRequest, NextResponse } from "next/server";

export async function GET(req: NextRequest) {
  const auth = req.headers.get("authorization");
  const expected = `Bearer ${process.env.CRON_SECRET}`;

  if (!process.env.CRON_SECRET || auth !== expected) {
    return NextResponse.json({ error: "unauthorized" }, { status: 401 });
  }

  // ... rest of handler unchanged
}
```

**Step 3 — Test locally** by passing the header manually:

```bash
curl -H "Authorization: Bearer your-secret" http://localhost:3000/api/cron/heartbeat
```

And verify it rejects a missing or wrong token:

```bash
curl http://localhost:3000/api/cron/heartbeat
# → {"error":"unauthorized"} with 401
```

**Why this matters:** Cron routes do real work — pinging internal services, triggering jobs, writing to a database. Without a guard, an attacker can hammer the endpoint (burning compute and rate limits), or trigger side effects on demand. The `CRON_SECRET` pattern is Vercel's own recommendation, costs almost nothing to add, and pairs naturally with the HMAC check on the webhook side: between these two you've locked down both inbound event surfaces in the app.
