## Suggested next step
Add **exponential-backoff retry** to the heartbeat cron — when the webhook probe fails, retry up to 3 times before declaring it unreachable. This teaches the most important reliability pattern in distributed systems and keeps it contained to a file you already own.

Replace the `fetch` block in `app/api/cron/heartbeat/route.ts` with:

```ts
async function probeWithRetry(url: string, maxAttempts = 3): Promise<"ok" | "unreachable"> {
  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    try {
      const res = await fetch(url, {
        method: "POST",
        headers: { "Content-Type": "application/json", "x-github-event": "ping" },
        body: JSON.stringify({ zen: "heartbeat probe" }),
      });
      if (res.ok) return "ok";
    } catch {
      // transient error — fall through to backoff
    }
    if (attempt < maxAttempts - 1) {
      await new Promise((r) => setTimeout(r, 2 ** attempt * 500)); // 500ms, 1s, 2s
    }
  }
  return "unreachable";
}
```

Then in the `GET` handler, replace the existing `try/catch` block with a single call:

```ts
const webhookStatus = await probeWithRetry(`${base}/api/webhooks`);
```

**Why this matters:** Real-world crons hit flaky networks and cold-start latency. A single-attempt probe will log false "degraded" statuses that hide real problems or trigger unnecessary alerts. The `2 ** attempt * 500` formula (exponential backoff) is the industry-standard shape — the base and multiplier vary by service, but the pattern is always the same. Understanding it here makes you fluent when you see it in Stripe webhook retries, GitHub Actions retry steps, or any queue consumer.
