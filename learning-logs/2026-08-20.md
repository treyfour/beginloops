Today's focus: **Heartbeats + Crons (locking your scheduled endpoint)**

Right now, `/api/cron/heartbeat` will run for anyone who sends a GET request to it — no secret required. In production on Vercel, that means the endpoint is publicly triggerable. The fix is simple: Vercel injects an `Authorization: Bearer <CRON_SECRET>` header on every cron invocation; your route checks it.

Here's the hardened route:

```ts
// app/api/cron/heartbeat/route.ts
import { NextResponse } from "next/server";

export async function GET(req: Request) {
  // --- 1. Authorize the caller ---
  const secret = process.env.CRON_SECRET;
  if (secret) {
    const auth = req.headers.get("authorization");
    if (auth !== `Bearer ${secret}`) {
      console.warn("[heartbeat] rejected — invalid or missing CRON_SECRET");
      return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
    }
  } else {
    console.warn("[heartbeat] CRON_SECRET not set — skipping auth (dev mode)");
  }

  // --- 2. Measure latency of the webhook probe ---
  const start = performance.now();

  const base = process.env.VERCEL_URL
    ? `https://${process.env.VERCEL_URL}`
    : "http://localhost:3000";

  let webhookStatus: "ok" | "unreachable" = "unreachable";
  try {
    const res = await fetch(`${base}/api/webhooks`, {
      method: "POST",
      headers: { "Content-Type": "application/json", "x-github-event": "ping" },
      body: JSON.stringify({ zen: "heartbeat probe" }),
    });
    webhookStatus = res.ok ? "ok" : "unreachable";
  } catch {
    webhookStatus = "unreachable";
  }

  const durationMs = Math.round(performance.now() - start);

  // --- 3. Return the health payload ---
  const payload = {
    status: webhookStatus === "ok" ? "ok" : "degraded",
    timestamp: new Date().toISOString(),
    durationMs,
    checks: { webhookEndpoint: webhookStatus },
  };

  console.log("[heartbeat]", JSON.stringify(payload));
  return NextResponse.json(payload);
}
```

**Set the secret in two places:**

```bash
# .env.local (dev)
CRON_SECRET=any-random-string-you-pick

# Vercel dashboard → Settings → Environment Variables → CRON_SECRET
# (Vercel automatically passes this header on cron invocations)
```

**Three concepts to lock in:**

1. **Vercel's cron auth is opt-in via `CRON_SECRET`.** Vercel reads this env var and injects `Authorization: Bearer <value>` on every scheduled cron call. Your route does nothing special to opt in — just check the header. Without `CRON_SECRET` set, the env var is absent and your guard falls through to the dev-mode warning, so local dev stays smooth.

2. **`performance.now()` gives sub-millisecond latency.** Unlike `Date.now()`, it uses the high-resolution timer and isn't subject to clock skew. Wrap the probe call, compute `performance.now() - start`, and you know exactly how long your webhook endpoint took to respond. If that number spikes, you have an early warning before users notice.

3. **Same concept, different transport.** Yesterday's webhook signature and today's cron secret both solve the same problem: "is this caller who they claim to be?" Webhooks use a payload signature (HMAC over the body); crons use a bearer token (HMAC-free, but the secret is never in the URL). Understanding both patterns covers the full surface area of server-to-server authentication in Next.js.
