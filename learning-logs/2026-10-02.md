Today's focus: **Webhooks — persisting received events between requests**

Right now your webhook handler logs incoming events and discards them the moment the handler returns. The next learning step is understanding *how to hold onto that data* — and exposing it through the same route file with a GET handler.

Update `app/api/webhooks/route.ts`:

```ts
// Module-level store — shared across requests in the same serverless instance.
// In production, replace this with a database (Upstash Redis, Vercel KV, Postgres).
const recentEvents: { timestamp: string; payload: unknown }[] = [];

export async function POST(request: Request) {
  const payload = await request.json();

  // Prepend new events, cap at 10 so memory stays bounded
  recentEvents.unshift({ timestamp: new Date().toISOString(), payload });
  if (recentEvents.length > 10) recentEvents.length = 10;

  console.log("Webhook received:", payload);
  return Response.json({ ok: true });
}

// A GET handler on the same file — Next.js App Router routes all HTTP methods here
export async function GET() {
  return Response.json({ events: recentEvents });
}
```

**Why this matters:**
- You learn the difference between *stateless* request handlers (each call is isolated) and *module-level state* (persists across calls within the same serverless instance). This is how serverless differs from a traditional always-on server.
- Adding `GET` to the same `route.ts` is how Next.js App Router handles multi-method routes — one file, multiple HTTP verbs. This pattern applies to every API route you'll ever write.
- The array here is a stand-in for a real store. Once you see it working, upgrading to Vercel KV or Upstash Redis is a single function swap — the "receive → store → expose" pattern stays identical.

Once this is in place, visit `/api/webhooks` in your browser to see stored events. That gives you real data to pull into `app/page.tsx` next.
