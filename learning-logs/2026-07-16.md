## Suggested next step
Add **exponential-backoff retries** to the heartbeat probe in `app/api/cron/heartbeat/route.ts`. A production heartbeat that gives up after one failure creates noisy false alarms; one that retries silently absorbs transient hiccups and only pages you on real outages.

Add this helper above the `GET` export:

```ts
async function probeWithRetry(url: string, retries = 3): Promise<"ok" | "unreachable"> {
  for (let attempt = 0; attempt < retries; attempt++) {
    try {
      const res = await fetch(url, {
        method: "POST",
        headers: { "Content-Type": "application/json", "x-github-event": "ping" },
        body: JSON.stringify({ zen: "heartbeat probe" }),
      });
      if (res.ok) return "ok";
    } catch {
      // transient failure — fall through to retry
    }
    if (attempt < retries - 1) {
      await new Promise(r => setTimeout(r, 200 * 2 ** attempt)); // 200ms, 400ms
    }
  }
  return "unreachable";
}
```

Then replace the try/catch block in `GET` with:

```ts
webhookStatus = await probeWithRetry(`${base}/api/webhooks`);
```

**Why this matters:** The `200 * 2 ** attempt` formula (200ms → 400ms → …) is the same exponential-backoff curve used in production monitoring systems everywhere — fetch, AWS SDK, Stripe's client, all of them. Once you see it once and write it yourself, you'll recognize it in every codebase. It also teaches a key heartbeat principle: a heartbeat that cries wolf on every transient blip gets ignored; a heartbeat that retries only escalates on *sustained* failures. This is the difference between on-call noise and on-call signal.
