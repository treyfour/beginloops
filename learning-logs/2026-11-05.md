Today's focus: **Crons — securing your cron endpoint with a shared secret**

Right now your heartbeat endpoint is wide open — anyone can hit it. Vercel Cron (and most cron providers) support sending a secret in the `Authorization` header to prove it's the real scheduler. Here's how to add it:

```ts
// app/api/cron/heartbeat/route.ts
import { NextResponse } from "next/server";

export async function GET(request: Request) {
  const auth = request.headers.get("authorization");
  if (auth !== `Bearer ${process.env.CRON_SECRET}`) {
    return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
  }

  // ... your existing heartbeat logic ...
  return NextResponse.json({ status: "ok", timestamp: new Date().toISOString() });
}
```

Then in `vercel.json`, Vercel automatically injects `CRON_SECRET` into the `Authorization` header when it invokes your cron. Add the env var to your Vercel project settings (Settings → Environment Variables) with a long random string.

**Why this matters:** Any cron endpoint that isn't protected is effectively a public GET route — anyone who discovers the URL can trigger it on demand, skew your metrics, or cause unintended side effects. The bearer-token pattern is the standard fix: a shared secret known only to your scheduler and your server. This same pattern applies to webhooks (you'll verify a signature instead of a token) and to any server-to-server call where you need to prove identity without a user session.
