Today's focus: **Heartbeats — making the heartbeat result readable without re-running checks**

Right now the heartbeat cron runs daily and logs its result to the console — then the data disappears. There's no way for the UI to see the latest heartbeat without triggering a new probe (which re-fetches `/api/webhooks`, which is wasteful). A cached status endpoint fixes this: the cron writes its result into an in-process store, and the UI reads it cheaply.

**Step 1 — Add a shared in-memory store in `app/api/_store.ts`:**

```ts
// Simple module-level cache — survives within a single serverless instance
export interface HeartbeatSnapshot {
  status: "ok" | "degraded" | "unknown";
  timestamp: string;
  checks: Record<string, string>;
}

let latest: HeartbeatSnapshot = {
  status: "unknown",
  timestamp: new Date(0).toISOString(),
  checks: {},
};

export function getSnapshot() { return latest; }
export function setSnapshot(s: HeartbeatSnapshot) { latest = s; }
```

**Step 2 — Make the heartbeat cron write into the store (`app/api/cron/heartbeat/route.ts`):**

```ts
import { setSnapshot } from "../_store";
// ... existing probe logic ...
setSnapshot(payload);           // add this line before returning
return NextResponse.json(payload);
```

**Step 3 — Create `app/api/status/route.ts`:**

```ts
import { NextResponse } from "next/server";
import { getSnapshot } from "../_store";

export async function GET() {
  return NextResponse.json(getSnapshot());
}
```

**Why this matters:** This is the heartbeat pattern in full: a scheduled probe writes a snapshot → a status endpoint exposes it cheaply → the UI reads it without triggering new I/O. Once `/api/status` exists, the `useHeartbeat` hook from yesterday's log can poll it instead of `/api/cron/heartbeat`, and your cron can run as often as you need without the UI creating extra traffic.
