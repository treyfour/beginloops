Today's focus: **Crons (authorization — protecting scheduled endpoints)**

Without this guard, any script on the internet can spam GET `/api/cron/heartbeat` and rack up function invocations against your Vercel quota. Worse, a malicious caller could trigger the endpoint intentionally to generate noisy logs or probe your internal routing. Vercel's cron runner forwards an `Authorization: Bearer <CRON_SECRET>` header on every scheduled invocation — checking that header before doing any work is the correct pattern.

**Step 1 — Set the secret in your environment:**

```bash
# .env.local (never commit this file)
CRON_SECRET=some-long-random-string
```

Register the same value in your Vercel project under **Settings → Environment Variables → CRON_SECRET**. The Vercel dashboard will automatically inject it into scheduled cron invocations.

**Step 2 — Add an auth check at the top of the GET handler:**

```ts
// app/api/cron/heartbeat/route.ts

import { NextRequest, NextResponse } from "next/server";

export async function GET(req: NextRequest) {
  // --- authorization guard ---
  const secret = process.env.CRON_SECRET;
  const authHeader = req.headers.get("authorization");

  if (!secret || authHeader !== `Bearer ${secret}`) {
    return NextResponse.json({ error: "unauthorized" }, { status: 401 });
  }
  // --- end guard; rest of handler unchanged ---

  const base = process.env.VERCEL_URL
    ? `https://${process.env.VERCEL_URL}`
    : "http://localhost:3000";

  let webhookStatus: "ok" | "unreachable" = "unreachable";
  let webhookLatencyMs: number | null = null;

  try {
    const t0 = performance.now();
    const res = await fetch(`${base}/api/webhooks`, {
      method: "POST",
      headers: { "Content-Type": "application/json", "x-github-event": "ping" },
      body: JSON.stringify({ zen: "heartbeat probe" }),
    });
    webhookLatencyMs = Math.round(performance.now() - t0);
    webhookStatus = res.ok ? "ok" : "unreachable";
  } catch {
    webhookStatus = "unreachable";
  }

  const payload = {
    status: webhookStatus === "ok" ? "ok" : "degraded",
    timestamp: new Date().toISOString(),
    checks: { webhookEndpoint: webhookStatus, webhookLatencyMs },
  };

  console.log("[heartbeat]", JSON.stringify(payload));
  return NextResponse.json(payload);
}
```

**Three concepts to lock in:**

1. **Fail closed, not open.** If `CRON_SECRET` isn't set in the environment, return 401 — don't fall through to processing. An unset secret means the environment isn't configured correctly; silently accepting the request hides a configuration bug.

2. **Bearer tokens are a convention, not magic.** The `Authorization: Bearer <token>` header is just a string — any HTTP client can send it. What makes it secure is that the token is a long random secret only Vercel and your environment know. Using a short or guessable secret defeats the purpose.

3. **Crons and webhooks share the same authorization pattern.** Both use a shared secret — the caller proves identity by presenting it, you verify it server-side and reject if it doesn't match. The only structural difference is that a cron secret goes in a header (`Authorization`), while a webhook secret is used to sign the *body* (HMAC). Once you've done one, the other is conceptually familiar.
