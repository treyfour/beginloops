## Suggested next step
Add a simple in-memory event log to your webhook handler so `GET /api/webhooks` returns the last 10 received events — this teaches you how webhook receivers store and surface history.

```ts
// app/api/webhooks/route.ts — add above the POST handler

// Module-level store: survives across requests within the same serverless instance.
// In production you'd use a database or KV store, but this is the right mental model.
const eventLog: { timestamp: string; payload: unknown }[] = [];
const MAX_EVENTS = 10;

export async function GET() {
  return Response.json({ events: eventLog });
}

export async function POST(req: Request) {
  const payload = await req.json();

  // Store the event (prepend so newest is first, cap at MAX_EVENTS)
  eventLog.unshift({ timestamp: new Date().toISOString(), payload });
  if (eventLog.length > MAX_EVENTS) eventLog.pop();

  // ... rest of your existing HMAC verification and handling
  return Response.json({ received: true });
}
```

Then visit `http://localhost:3000/api/webhooks` in your browser — you'll see a JSON list of events that grew each time the heartbeat cron (or any other caller) hit the POST endpoint.

**Why this matters:** Most real webhook systems pair a receiver (`POST`) with an inspector (`GET`) — Stripe's dashboard, GitHub's delivery history, and Svix's event log all follow this exact pattern. The in-memory array is a starting point; swapping it for `@vercel/kv` or a Postgres table is one line of logic change because the route structure stays identical. Understanding the store-then-query shape here is the foundation for building any observable, debuggable event pipeline.
